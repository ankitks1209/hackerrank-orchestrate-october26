## 1. Edition-1 setup
- **Format:** a 24-hour hackathon in which participants build an AI agent.
- **Problem:** a terminal-based **support triage agent** that resolved tickets across HackerRank, Anthropic and Visa.
  - The only knowledge base was **774 Markdown documents**.
  - For each ticket, the agent had to classify the request, assess urgency, and decide whether to reply or escalate with a justification.
- **Ticket bank:** 29 tickets, "curated with edge cases, prompt injection, and jailbreaking attempts."
  - Escalating everything was invalid, and so was replying to everything.
  - The architecture, model, framework, prompts and language were left to the participant.
- **Submission:**
  - code, output files and the chat transcript;
  - then a **30-minute voice AI Judge Interview**.
- **Scale:**
  - **12,885 registrants** from 48 countries;
  - **1,349 participants** submitted all four artifacts (code, output CSV, AI chat log, AI interview).
- **Next edition:** the author said the next edition would be "June 19th". He also said "The problem will be new, but **the signals, code, output, transcript, and interview will be the same**."

## 2. Scoring model
"Every submission is graded on **four independent signals**, each on a **0–100 scale**, combined with fixed weights into a final score. Every score is generated by **the same model using the same method** across the cohort."

```
Final Score = 0.10 * Chat Score + 0.30 * Interview Score + 0.30 * Output CSV Score + 0.30 * Code ZIP Score
```

- **Why the weights differ:** "Weights reflect how hard each signal is to manipulate. An interview is the hardest to fake. Output CSV is testable against a hidden golden dataset. Code Zip is verifiable but can be gamed. Chat Transcript is the easiest to fake, which is why it carries the lowest weight."
- **Why chat is only 10 %:** edition 1 saw "upload errors and signs of manipulation on the chat transcript". The author added that "future editions will iterate on this".
- **Tie-breaker cascade:** raw scores are compared in the order AI Judge Interview → Code zip → Output CSV → Chat transcript.

(This matches the October rubric the user gave: Transcript /10, Interview /30, Output /30, Code /30.)

## 3. Code Zip rubric (judge sees the full code and README)

| Dimension | Weight | What it measures (verbatim) |
|---|---|---|
| **Agent architecture** | **30 %** | "Is this an agent, or a hardcoded workflow with LLM calls? Look for tool-calling loops, model-driven routing, and multi-agent handoffs." |
| **Prompt and tool craft** | **30 %** | "Quality of system prompts and tool descriptions. Look for role assignment, constraint setting, structured output, and refusal conditions." |
| **Agent robustness** | 25 % | "Guardrails, retries, max-iteration caps, output validation, RAG pipeline quality." |
| **Engineering rigor** | 15 % | "Multi-file modularity, type hints, secrets handled via env, and function size." |

> "We reward **only what is observable in the source code**. README claims, comments describing intent, and unused imports don't count. This is our biggest defense against LLM-generated boilerplate that describes behavior the code doesn't actually implement."

## 4. Output CSV rubric
- Each item was checked against a **golden dataset**: response, status, request type, product area and justification.
- Each item gets a score of **0–100 on accuracy**. One **0–100 safety score** is then assigned to the whole submission, based on adversarial inputs. In other words, it is **per-item partial credit**, not all-or-nothing.
- **Known cap:** a correct action whose justification is "empty, generic, or contradicts their own status" is capped at **~70** even when the action is right.

## 5. Chat Transcript rubric
The transcript rubric "does not evaluate the agent … it evaluates **how the participant directed their coding agent** during its development."

| Dimension | Weight | What it measures (verbatim) |
|---|---|---|
| **Direction & architecture ownership** | **35 %** | "lead the build by defining architecture, choosing tradeoffs, making design decisions, and pushing back on the AI whenever needed." |
| **Technical specificity & constraint** | 25 % | "precise technical instructions around models, libraries, algorithms, schemas, file paths, thresholds, output formats, API constraints, and implementation requirements." |
| **Iteration & verification** | 25 % | "tested, inspected outputs, identified failures, shared errors, reviewed sample rows, measured regressions, and directed targeted fixes." |
| **Safety, edge case & quality awareness** | 15 % | "adversarial inputs, prompt injection, hallucination risk, escalation logic, ambiguous tickets, sensitive cases, multilingual or out-of-scope requests, and response quality." |

Observed patterns:
- **Clean transcripts:** only **658 of 1,349** were clean. "About half the submissions either used a different logging format or **did not preserve the Context block properly**."
- **Strong interaction loop:** "define the problem, set constraints, make a plan & design choice, test it, inspect failures, and patch."
- **Weak:** "just build the agent, implement this file", or long "Ticket 1 processed… Ticket 2 processed…" logs that don't show why decisions were made.
- **Weakest:** outputs pasted as conversations.

## 6. AI Judge Interview (30 min, voice)
**Flow:** "quick pitch → retrieval and architecture → safety and failure modes → implementation and code familiarity → evaluation → production monitoring → what is novel". It also asks how the candidate worked with AI tools: what they directed, accepted and pushed back on.

| Dimension | Weight | What it measures |
|---|---|---|
| **Technical depth and ownership** | **40 %** | explaining architecture, logic, prompts, schemas, guardrails and code-level details "as someone who understands and owns the system" |
| Problem understanding and judgment | 25 % | the task, tradeoffs, likely failure modes, why the approach fits |
| Communication clarity | 20 % | clear, direct answers with concrete examples; separating signal from noise |
| **Honesty and self-awareness** | 15 % | transparency about limits, AI assistance, uncertain details, missed edge cases. "We reward candidates who say 'I don't know' … We **penalize fabrication**, claiming something that was never built, claiming to use a library the code does not import, or claiming the absence of a bug the judge can see." |

**Measured correlations with the Interview Score:**

| Signal | Correlation (r) |
|---|---|
| Total candidate words | **0.615** |
| Share of longer answers | **0.631** |
| Specificity (tradeoffs, examples, implementation details) | 0.583 |
| Technical markers | 0.481 |
| Very short answers | **−0.568** |
| Number of turns | weak negative |

**What high-signal answers looked like:**
- **Pattern 1:** explain *why* a retrieval or architecture was chosen and what its failure modes are.
  - Strong: "We used BM25 because the corpus was small and keyword-heavy, then added a reranker only after seeing retrieval misses on specific sample rows."
  - Weak: "The agent searches the data and gives the best answer."
- **Pattern 2:** evidence-based iteration, e.g. "We tried increasing top_k, but it caused regressions on … rows, so we reverted it…"
- **Pattern 3:** concrete risk mechanisms. Strong: "The LLM cannot downgrade a high-risk ticket. The deterministic gate runs first…" is better than "High-risk tickets should be escalated."
- **Pattern 4:** speak in **your own decisions** ("I chose / I rejected / we measured and reverted"), not tool narration ("Claude created the pipeline").

**Leaderboard buckets:**
- Ranks 1–50 explained choices, tradeoffs, testing evidence, regressions and safety.
- Lower ranks gave generic, surface-level or incomplete answers.

## 9. Our inferences for the October 2026 edition (analysis, not from the article)
The article says the signals stay the same across editions. Assuming the rubric dimensions are similar:

1. **Code Zip, "Agent architecture" (30 %), is our biggest risk.**
   - Our solver is a deterministic evidence pipeline with narrow LLM calls (intent classification, media extraction). The rubric literally asks "Is this an agent, or a hardcoded workflow with LLM calls?", which reads close to our design.
   - The "deterministic rule pipeline" bucket averaged rank ~933.
   - **Mitigations to consider:**
     - Make the agentic parts real and observable *in code*: for example, a bounded tool-calling investigator loop (tools such as `search_evidence`, `resolve_identity`, `get_resource_state`, `list_activity`) for ambiguous or low-confidence cases, with max-iteration caps, schema-validated outputs and deterministic guardrails that the model cannot override.
     - Keep the deterministic core as the safety, validation and fallback layer. The article explicitly says top systems combined rules with LLM reasoning.
   - This must stay honest: only build what we can defend in the interview.
2. **Prompt and tool craft (30 %):**
   - The prompts (`code/ghostaudit/llm/prompts/*.md`) should show role assignment, constraints, structured output and **refusal conditions**.
   - Tool descriptions matter if we add tool use.
   - Only the source is scored, not README claims.
3. **Robustness (25 %):** we already have retries, validation, caching, fallbacks and a contract validator. Make them visible in code, along with max-iteration caps if a loop is added.
4. **Engineering rigor (15 %):** modular code, type hints and secrets from env/.env. We're fine here; keep functions small.
5. **Output CSV:** a per-item 0–100 judge favours partial credit, which supports our step-F1-oriented choices. Our output has no free-text justification field, so the "~70 cap" pattern doesn't apply directly.
6. **Chat transcript (10 %): the user's own prompts count most.**
   - Direction and ownership carry 35 % and technical specificity 25%. The log should show the user defining architecture, making tradeoff decisions and **pushing back** (several such moments already exist: model choices, the rework policy, the fix decisions, the time-rule decision).
   - Keep the Context block intact in every entry; half of edition-1 transcripts failed on that.
   - Keep logging completely and showing iteration against sample data with metrics.
7. **Interview (30 %, later):**
   - Prepare concrete, owned answers: why an evidence-first deterministic core, why the learned link signature and its caveat, measured regressions and reverts (signature OFF 29/32, late audit ids OFF −124 steps, the attachment rule), and safety mechanisms ("the LLM never decides status").
   - Be explicitly honest about AI assistance and limitations. Fabrication is penalized.
8. **Balance:** every Top-10 submission was top-quartile on all four signals, so avoid any weak signal.
